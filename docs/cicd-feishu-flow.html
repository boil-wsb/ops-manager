CICD 流水线接收与飞书通知

代码仓库出事件 → 判断该不该通知 → 发出卡片 → 后续更新同一张卡 → 用户点按钮

文字版：cicd-feishu-flow.md

1两个角色

接收方不碰飞书，投递方不碰业务。整条链只有一次交接。

开始 / 结束 处理 判断 交接 / 产出 异常路径

一句话：凭证只留在投递方，任何系统想发飞书消息都得经过它 —— 于是记录、查重、一次通知多群都成了投递方的内建能力。

2事件入口

两类事件处理方式完全不同，两类流水线直接忽略。

一句话：提交只记录不发通知 —— 用户关心的是构建结果，不是代码变动；忽略那两类流水线是为了不制造重复和噪音。

3标识与建卡

唯一标识必须带项目，否则不同项目的同号流水线会互相覆盖。

一句话：一条流水线从开始跑到结束只对应一张卡 —— 用户在飞书里看到的是同一张卡在变，而不是每来一次事件就刷一张新的。

4三级退让

主路径失败就往下退一级，而不是一失败就报错。三级依次向下，结果只有两种。

开始 主路径 兜底路径 失败退让 虚线为降级或兜底

一句话：投递方整体宕机时，一条不完美的通知远好过完全静默 —— 但代价是拿不到卡片身份，所以只有走前两级才记卡片标识。

5投递方发卡

查重条件必须带上收件人，否则「一次通知多群」时会漏发。

一句话：查重条件不带收件人，第一个群发成功后后续群会被误判成重复而收不到 —— 漏发比重复发严重得多。

6用户操作

转交必须换掉按钮，否则用户会反复点。

一句话：业务系统必须快速响应，否则用户看到的是「操作无响应」；失败时先释放资源再记原因，顺序颠倒会耗尽资源。

7超时盯守

每分钟扫一遍，按超时倍数分三档，同一档位只提醒一次。

开始 / 结束 处理 判断 / 档位 忽略 / 跳过 反向路径

一句话：升级时更新原卡而不是新建，否则同一个构建会因越来越超时而刷出好几张卡；发送失败要清掉档位标记，否则这个构建永远不会再被提醒。

8规则速记

整个链路只有四条底线，其余都是从这四条推出来的。

一句话：代码仓库出事件 → 判该不该通知 → 发卡 → 后续更新同一张卡 → 用户点按钮；全程守住这四条。
