# CICD 流水线接收与飞书通知业务流程

> 整理时间：2026-09-22
> 配套流程图：[docs/cicd-feishu-flow.html](./cicd-feishu-flow.html)

---

## 一、为什么是两个角色

| 角色 | 只管一件事 |
|---|---|
| **事件接收方** | 听代码仓库的动静、判断该不该通知、决定通知什么内容。不碰飞书。 |
| **消息投递方** | 独占飞书凭证、把卡片发出去、记录每次发送、处理用户在飞书上的操作。不碰流水线业务。 |

**这样拆换来三件事**：

1. **凭证不外泄** — 谁想发飞书消息都必须经过投递方。
2. **天然可审计** — 每张卡片都有记录：发给了谁、更新过几次、成没成。
3. **一次通知多群** — 接收方只需说「发这几个群」，投递方负责逐条发出、逐条更新。

## 二、一条流水线的完整生命周期

### 2.1 收到事件

事件只有两类，处理方式完全不同：

- **代码提交** → 记下来，不通知。用户关心的是构建结果，不是代码变动本身。但这条记录要留着，因为后面要和流水线事件互相补全信息。
- **流水线状态变化** → 继续往下走。

流水线事件里有两类**直接忽略**：由上级流水线触发的下级（上级已经通知过了）、为合并请求临时跑的（不是正式构建发布）。忽略是为了不制造重复和噪音。

事件顺序不保证。提交和流水线可能乱序到达，所以两边都要在对方到达时互相补全。

### 2.2 记录并生成标识

记下：项目、分支、流水线编号、各阶段进度、部署到哪台机器。

**然后生成这次通知的唯一标识 —— 这是整套设计里最关键的一处修正。**

标识必须由「**项目 + 流水线编号**」共同组成。

原因是：流水线编号只在单个项目内唯一。A 项目有第 5010 号，B 项目也有第 5010 号。早期只用编号做标识，两个项目的卡片会互相覆盖——A 的通知发出去后，B 的通知把它更新掉了。

这个标识有两个用途：**认出这是哪次流水线**、**校验更新权限**（防止误改别人的卡片）。

### 2.3 判断新建还是更新

看系统里有没有这次流水线的卡片信息。没有就新建，已有就更新。

**效果**：一条流水线从开始跑到结束，用户在飞书里始终只看到**一张**卡片在变化，而不是每来一次事件就刷一张新的。这是防刷屏的核心。

### 2.4 发出通知

**三级退让**：已经有卡片就原地更新 → 还没有就新建 → 前两级都失败就走备用通道。

为什么要留第三级：如果投递方整体宕机，前两级都会失败。这时候宁可发一条「不完美、后续没法再更新」的通知，也好过完全静默——用户至少知道出事了。

第三级的代价：拿不到卡片身份，**后续无法再更新它**。所以只有走正式通道才记卡片标识。

### 2.5 流水线结束时

| 状态 | 做什么 |
|---|---|
| 失败 | 找失败原因，补发一条说明 |
| 成功 | 检查是否需要触发后续动作（如自动部署） |

**找失败原因也是三级退让**：向代码仓库要日志 → 拿不到就查本地留存 → 都没有就如实告知「暂时无法获取」。第二级的存在是因为外部接口会限流、超时、权限失效。

失败通知**固定发统一的运维群**，不是各项目自己的群——失败要运维介入，发到统一群里才有人盯着。

### 2.6 用户在卡片上操作

**分支一：转交给别人** — 把原卡片内容发给被转交人，然后把原卡片上的「转交」按钮换成一句状态说明。

换掉按钮是必须的：按钮还在，用户就会反复点，导致反复转发。

**分支二：通知业务系统** — 把用户操作整理成一份说明（哪张卡、谁点的、点了什么、什么时间），送达业务系统预留的地址。

送达时限要求严格。业务系统卡住，用户会看到「操作无响应」。

## 三、投递方在做什么

### 3.1 发卡片

```
校验请求 → 判断是否重复 → 确认收件人 → 发出 → 记录并回传卡片身份
```

**校验**：发给个人和发给群必须二选一。要「点击后通知业务系统」就必须给卡片标识，否则系统不知道该把这次点击归到哪张卡上。

**判断是否重复**（最重要的一道防线）：

接收方发起通知后有等待时限。投递方响应慢了，接收方会判定失败并重发，用户就看到两张一样的卡片。所以投递方记一笔「这个标识 + 这个收件人已经成功发过了」，第二次直接返回。

**这里有个必须注意的细节：判断条件必须带上收件人。**

因为同一条通知可能发多个群。只按标识判断的话，第一个群发成功后，第二个群的请求会被误判成重复，导致**第二个群收不到**。漏发比重复发严重得多。

**确认收件人**：发给群直接用群标识（内部加前缀与个人区分）；发给个人按三级顺序找——先按名字、再按姓名加身份、最后直接按身份。

找不到要区分两种情况：**完全找不到这个人**（调用方给错名字了）和**找到了但没绑飞书**（需要去补绑账号）。处理方式完全不同。

**回传卡片身份**：如果调用方本来没给标识（说明是首次发送），就把飞书返回的真实身份回传给它，它后续就知道该用哪个标识来更新了。

### 3.2 更新卡片

**按卡片身份更新单张**：先校验记录存在、业务标识一致，才允许改。校验是为了防止调用方拿错身份把别人的卡片改掉。

**按业务标识批量更新**（对应一次通知多群）：找出该业务下的所有卡片，但**只挑发送成功且确实拿到卡片身份的**——没发成功的不存在卡片，走了备用通道的没身份无从更新，挑出来只会报错。

每个群单独更新，一个群失败不影响其他群。所有群都成功才算整体成功。

### 3.3 处理用户操作

先识别用户点的是什么动作。正常从按钮携带的信息里读；读不到就按按钮文字猜（保底，避免配置遗漏导致功能失效）。在输入框打字的事件不处理。

**重复点击要忽略**：有些动作不允许同时跑两份（比如数据同步），系统记下「这个动作正在跑」。

然后按动作走 2.6 里的两个分支。

## 四、五条关键规则

### 规则一：唯一标识必须带项目

流水线编号只在项目内唯一。不带项目，不同项目的同号流水线会互相覆盖。

### 规则二：一条流水线只对应一张卡

后续所有状态变化都是更新原卡，不是新建。这是防刷屏的根本。

### 规则三：判断重复必须带收件人

只按标识判断，会让「一次通知多群」场景下的后续群被误判成重复而漏发。

### 规则四：退让优先于报错

系统在四处采用「主路径失败就退一步」：发送通知（更新→新建→备用通道）、找失败原因（外部→本地→告知）、找人（三级匹配）、识别提交（多路匹配）。

共同意图：**优先保证事情办成，而不是办得漂亮**。一条不完美的通知远好过什么都没有。

### 规则五：顺序不能颠倒的两处

- **失败记录必须在释放资源之后**。颠倒会导致连接资源被耗尽。
- **转交卡片必须换掉按钮**。不换，用户就会反复点。

## 五、防重复的三道关卡

| 关卡 | 在哪 | 防什么 |
|---|---|---|
| 一 | 投递方 | 防接收方超时重发造成重复卡片 |
| 二 | 超时盯守 | 防同一档位的超时提醒反复发送 |
| 三 | 动作处理 | 防用户重复点击同一动作 |

---

## 六、超时盯守

一条独立的巡逻任务，每分钟扫一遍正在跑的构建。

- **先排除**：项目在免盯名单、提交带免盯标记、构建已取消。
- **判档**：按超出该项目容忍时长的倍数分三档——刚到或略超 / 超 3 倍 / 超 6 倍。
- **去重**：同一档位只提醒一次，否则每分钟提醒一次就成了骚扰。
- **重试**：提醒发送失败就把档位标记清掉，下一轮重新发。不清掉的话这个构建永远不会再被提醒。
- **升级时更新原卡而非新建**，否则同一个构建会因越来越超时而刷出好几张卡。

---

## 七、并发与保存

| 场景 | 处理 | 原因 |
|---|---|---|
| 超时提醒发送 | 控制同时发送数量 | 大量构建同时超时会压垮系统 |
| 同一项目的部署 | 串行 | 部署共用同一份产物目录，并发会互相覆盖 |
| 不同项目的部署 | 可以并发 | 产物目录互不干扰 |
| 数据同步 | 同一动作只跑一份 | 重复跑无意义 |

数据存两层：**内存**（读写快，支撑实时查询与更新）+ **持久化**（重启后能恢复）。启动时从持久化恢复到内存。内存有上限，超限按时间淘汰最旧的。

## 八、异常与反应

| 情况 | 反应 |
|---|---|
| 事件是代码提交 | 只记录，不通知 |
| 下级 / 合并请求流水线 | 忽略 |
| 首次通知 / 状态变化 | 新建卡片 / 更新原卡 |
| 走了备用通道 | 能发出，但后续无法更新 |
| 同一通知重复请求 | 直接返回，不重复发送 |
| 一次通知多个群 | 各发各的，不互相误判 |
| 找不到人 | 告知用户不存在 |
| 找到但没绑飞书 | 告知未绑定，无法发送 |
| 更新时业务标识对不上 | 拒绝更新 |
| 更新时找不到记录 | 告知未找到 |
| 批量更新一条都没有 | 告知未找到可更新的记录 |
| 飞书响应慢 | 自动重试，间隔逐次拉长 |
| 向仓库要日志失败 | 改用本地留存 |
| 本地日志也没有 | 告知暂时无法获取 |
| 构建超时 | 按档位提醒，升级时更新原卡 |
| 转交失败 | 提示「转交失败，请稍后重试」 |
| 通知业务系统失败 | 先释放资源，再记原因 |
| 用户重复点击同步 | 忽略 |
| 投递方整体不可用 | 退到备用通道 |
| 备用通道也不可用 | 记录失败，放弃本次 |

---

## 九、主线一句话

代码仓库出事件 → 接收方判断该不该通知、生成带项目的唯一标识、决定新建还是更新 → 投递方查重、找到收件人、发出并回传卡片身份 → 后续状态变化更新同一张卡 → 用户点按钮，转交或通知业务系统。

全程四条底线：**标识带项目、一流水线一张卡、查重带收件人、退让优先于报错。**
